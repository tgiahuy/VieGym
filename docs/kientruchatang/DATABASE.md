> Thiết kế dữ liệu quan hệ cho ứng dụng quản lý sức khỏe, luyện tập, dinh
> dưỡng và AI Coach cá nhân hóa VieGym.

> **Phiên bản tài liệu:** 1.2 — 2026-08-31
> **Hệ quản trị:** PostgreSQL 16+
> **Nguồn yêu cầu:** [SRS v3.2](../spec/specs.md),

## 1. Mục tiêu và phạm vi

PostgreSQL là **source of truth** cho identity, hồ sơ, sức khỏe, luyện tập,
dinh dưỡng, consent, recommendation và audit. Schema này phục vụ Spring Boot
modular monolith; Flutter và FastAPI AI Service không truy cập database trực
tiếp.

Các nguyên tắc bắt buộc:

- Backend là thành phần duy nhất thực thi mutation nghiệp vụ và tính các metric
  authoritative.
- Mọi dữ liệu cá nhân có `user_id` trực tiếp hoặc ownership path rõ ràng.
- Foreign key, unique constraint, check constraint và transaction bảo vệ các
  invariant quan trọng; authorization/ownership vẫn phải kiểm tra ở service.
- `MealEntry`, workout log và AI proposal lưu snapshot cần thiết để lịch sử
  không đổi khi master data thay đổi.
- Binary ảnh/video nằm trong S3-compatible object storage; PostgreSQL chỉ lưu
  metadata và object key.
- Schema được version hóa bằng Flyway. Không dùng Hibernate/JPA
  `ddl-auto=update` ở staging/production.
- Dashboard là read model tổng hợp từ dữ liệu đã commit, không có bảng nguồn sự
  thật riêng trong P0.
- Redis chỉ là cache/rate-limit tùy chọn; mất Redis không được làm mất session
  hoặc business record authoritative.

Ký hiệu phạm vi:

- **P0:** bắt buộc cho MVP/demo.
- **P1:** chỉ triển khai sau khi P0 ổn định.
- Các bảng không ghi chú là P0.

## 3. Quy ước nền tảng

### 3.1. Naming, key và timestamp

- Tên bảng/cột dùng `snake_case`, danh từ số nhiều cho bảng.
- Primary key mặc định: `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- Bảng liên kết dùng composite primary key nếu không cần định danh riêng.
- Entity mutable có `created_at TIMESTAMPTZ NOT NULL DEFAULT now()` và
  `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`.
- Timestamp lưu UTC; API/UI chuyển sang timezone người dùng.
- Ngày nghiệp vụ như ngày ăn, ngày tập, ngày cân dùng `DATE`.
- Khối lượng lưu bằng kilogram, chiều cao bằng centimeter, thời lượng bằng
  second, năng lượng bằng kcal và macro bằng gram.
- Giá trị đo/tính dùng `NUMERIC`, không dùng floating point cho dữ liệu
  authoritative.
- Email được normalize lowercase/trim trước khi lưu. Unique email nên dùng
  index trên `lower(email)` để chống trùng khác hoa/thường.
- JSON linh hoạt dùng `JSONB`, nhưng các field cần join/filter/constraint phải
  là cột quan hệ thông thường.

Ứng dụng có thể ánh xạ các giá trị dưới đây bằng `VARCHAR` + `CHECK` để migration

### 3.3. Soft delete và retention

| Entity | Chính sách |
|---|---|
| `users` | Dùng `deleted_at`; không cascade xóa lịch sử nghiệp vụ/audit. |
| `exercises`, `foods` | Dùng `visibility = HIDDEN` và `deleted_at`; lịch sử vẫn giữ FK/snapshot. |
| `workout_programs` | Archive/soft delete; không xóa log đã hoàn thành. |
| `media_objects` | Chuyển trạng thái/orphan trước khi xóa object vật lý. |
| Token, OTP | Có thể hard-delete sau thời hạn retention bảo mật. |
| Log nghiệp vụ, consent, recommendation, audit | Không soft delete trong runtime demo; purge cùng reset môi trường theo runbook đồ án tốt nghiệp. |

Không đặt `ON DELETE CASCADE` từ `users` vào dữ liệu sức khỏe, workout,
nutrition, AI hoặc audit. Cascade chỉ phù hợp với thành phần cấu hình chưa tạo
lịch sử, ví dụ `workout_day → workout_exercise`, và vẫn phải do use case kiểm
soát.

## 4. Identity & Profile Domain

### 4.1. `users`

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | BIGINT | PK, IDENTITY | Định danh user |
| `email` | VARCHAR(255) | NOT NULL | Email đã normalize; unique không phân biệt hoa thường |
| `password_hash` | VARCHAR(255) | NULLABLE | BCrypt/Argon2 hash; null với tài khoản social-only |
| `auth_provider` | VARCHAR(20) | NOT NULL | `LOCAL`, `GOOGLE`, `FACEBOOK` |
| `provider_subject` | VARCHAR(255) | NULLABLE | Subject do Google/Meta xác minh server-side |
| `role` | VARCHAR(20) | NOT NULL, DEFAULT `USER` | `USER`, `ADMIN` |
| `status` | VARCHAR(20) | NOT NULL, DEFAULT `PENDING` | Trạng thái account |
| `email_verified_at` | TIMESTAMPTZ | NULLABLE | Thời điểm verify email |
| `last_login_at` | TIMESTAMPTZ | NULLABLE | Login thành công gần nhất |
| `deleted_at` | TIMESTAMPTZ | NULLABLE | Soft delete/deactivate |
| `created_at`, `updated_at` | TIMESTAMPTZ | NOT NULL | Audit timestamp |

Constraints/index chính:

- `UNIQUE INDEX uq_users_email_ci ON users(lower(email))`.
- Unique partial `(auth_provider, provider_subject)` khi `provider_subject IS NOT NULL`.
- Email trùng với account/provider khác không được tự động liên kết; P0 trả conflict và yêu cầu flow liên kết có xác thực.
- Local account phải có `password_hash`; account `ACTIVE` phải đã verify theo
  flow tương ứng.

## 5. Health & Body Domain

### 5.1. `health_profiles`

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | BIGINT | PK, IDENTITY | Health profile |
| `user_id` | BIGINT | FK → `users(id)`, NOT NULL, UNIQUE | Quan hệ 1:1 |
| `date_of_birth` | DATE | NOT NULL | Backend suy ra age tại thời điểm tính |
| `gender` | VARCHAR(20) | NOT NULL | Gender enum |
| `calculation_sex` | VARCHAR(20) | NOT NULL, DEFAULT `UNSPECIFIED` | Input riêng cho BMR; không suy ra từ gender |
| `height_cm` | NUMERIC(5,2) | NOT NULL, CHECK > 0 | Chiều cao chuẩn hóa |
| `current_weight_kg` | NUMERIC(6,2) | NOT NULL, CHECK > 0 | Cân nặng authoritative hiện tại |
| `activity_level` | VARCHAR(20) | NOT NULL | Activity level |
| `fitness_goal` | VARCHAR(30) | NOT NULL | Mục tiêu |
| `training_experience` | VARCHAR(30) | NOT NULL | Kinh nghiệm tập luyện |
| `bmi` | NUMERIC(6,2) | NOT NULL, CHECK > 0 | Backend tính |
| `bmr_kcal` | NUMERIC(8,2) | NULLABLE, CHECK > 0 | Mifflin-St Jeor khi đủ dữ liệu/rule |
| `tdee_kcal` | NUMERIC(8,2) | NULLABLE, CHECK > 0 | BMR × activity factor khi tính được |
| `calculation_version` | VARCHAR(30) | NOT NULL | Phiên bản rule tính |
| `calculated_at` | TIMESTAMPTZ | NOT NULL | Thời điểm tính gần nhất |
| `created_at`, `updated_at` | TIMESTAMPTZ | NOT NULL | Audit timestamp |

Không cho client ghi trực tiếp `bmi`, `bmr_kcal`, `tdee_kcal`. Cập nhật chiều
cao, cân nặng profile, activity hoặc goal phải recalculation trong cùng
transaction. Khi `calculation_sex=UNSPECIFIED` hoặc age dưới 18, chỉ BMI được
tính khi đủ dữ liệu; BMR/TDEE/target để null và API trả
`calculationStatus=INCOMPLETE` với reason `CALCULATION_SEX_REQUIRED` hoặc
`UNSUPPORTED_AGE`. Backend không được suy ra `calculation_sex` từ `gender`.
Sau onboarding, `current_weight_kg` không có endpoint cập nhật độc lập: chỉ
WeightLog mới nhất theo `(logged_date, updated_at)` được đồng bộ vào profile và
kích hoạt tính lại BMI/BMR/TDEE. WeightLog cũ hơn chỉ sửa lịch sử/trend.

### 5.3. `weight_logs`

| Column | Type | Constraints | Description |
|---|---|---|---|

## 10. Constraint và lifecycle bắt buộc

### 10.1. State machines

```text
Account: PENDING --OTP verify--> ACTIVE

WorkoutSchedule:
PLANNED ──► COMPLETED | MISSED | CANCELLED

WorkoutSession:
IN_PROGRESS ──► PAUSED ──► IN_PROGRESS
          └──────────────► COMPLETED
IN_PROGRESS | PAUSED ────► DISCARDED

AiRecommendation:
PENDING ──► APPLIED | DISMISSED | EXPIRED

MediaObject:
PENDING_UPLOAD ──► READY | FAILED
PENDING_UPLOAD quá TTL ──► ORPHANED
READY/FAILED/ORPHANED ──► DELETED
```

Database `CHECK` bảo vệ tập giá trị và hình dạng terminal state; domain service
bảo vệ transition hợp lệ. `MISSED` được materialize idempotent bởi job hoặc lazy
trước read sau khi qua cuối ngày + grace period theo profile timezone. Không
đánh `MISSED` khi schedule có session active. Recommendation expiry cũng có thể
scheduled/lazy nhưng phải cùng một rule authoritative.

### 10.2. Invariant quan trọng

| Invariant | Cơ chế |
|---|---|
| Email duy nhất không phân biệt hoa thường | Unique expression index `lower(email)` |
| Một HealthProfile/User | `UNIQUE health_profiles(user_id)` |
| Một NutritionTarget hiện hành/User | `UNIQUE nutrition_targets(user_id)` |
| Một WeightLog/User/Ngày | `UNIQUE (user_id, logged_date)` |
| Tối đa một active WorkoutProgram/User | Unique partial index |
| Tối đa một active Session/User và một session/Schedule | Unique indexes |
| Một WorkoutLog/Session | `UNIQUE workout_logs(workout_session_id)` |
| Một MealPlan/User/Ngày | `UNIQUE (user_id, plan_date)` |
| Một ConsentSetting/User | `UNIQUE ai_consent_settings(user_id)` |

## 12. Transaction boundaries và concurrency

| Use case | Transaction boundary |
|---|---|
| Verify register OTP | Consume OTP → activate account → tạo/cấp session metadata |
| Update Health Profile | Validate input → update profile → tính BMI/BMR/TDEE → upsert NutritionTarget |
| Add WeightLog | Upsert (`user_id`, `logged_date`) → nếu là log mới nhất thì sync current weight và tính lại BMI/BMR/TDEE; không tự đổi NutritionTarget |
| Finish Workout Session | Lock session/schedule → validate logs → persist snapshots/set logs → calculate volume/PR → mark completed |
| Update MealEntry | Validate owner/Food → calculate nutrition snapshots → save; totals được aggregate lại |
| Change AI Consent | Update current setting → append consent history |
| Generate Daily Recommendation | Tạo/lock generation ngắn → gọi provider ngoài transaction → validate batch → expire PENDING batch cũ cùng ngày + persist 1–3 items + mark SUCCEEDED atomically; FAILED không tạo item |
| Apply Recommendation | Lock/version check → ownership/state/expiry/action validation → domain mutation → recommendation log/audit → APPLIED |
| Dismiss Recommendation | Lock/version check → log feedback → DISMISSED; không mutation domain |

Lời gọi AI provider và object storage là external side effect, không nằm trong
distributed transaction với PostgreSQL. Backend phải lưu trạng thái có thể
retry/fallback (`ai_requests`, `media_objects`) và không giữ database transaction
mở trong lúc chờ provider lâu.

## 13. Calculation và snapshot rules

### Health

```text
BMI = weightKg / (heightM * heightM)
BMR (male)   = 10*weightKg + 6.25*heightCm - 5*age + 5
BMR (female) = 10*weightKg + 6.25*heightCm - 5*age - 161
TDEE = BMR * activityFactor
```

Backend lưu kết quả cùng `calculation_version`; công thức/rule thay đổi không
được âm thầm viết lại lịch sử. Tuổi là số năm tròn tại ngày tính theo profile
timezone. Mọi kết quả authoritative dùng decimal và round `HALF_UP` tới hai chữ
số sau dấu phẩy; golden tests khóa input/output cho `health-v1`.

Rule `health-v1` dùng offset calories theo goal `-400/0/+400/+300` lần lượt cho
`LOSE_WEIGHT/MAINTAIN_WEIGHT/GAIN_WEIGHT/GAIN_MUSCLE`; protein factor
`2.0/1.4/1.6/2.0 g/kg` theo cùng thứ tự và fat ratio `25%`. Không tạo/upsert
`nutrition_targets` nếu calories dưới `1200`, carb âm hoặc kết quả không hữu
hạn/dương. Lưu tối đa hai chữ số thập phân; rounding hiển thị thuộc Mobile.

### Workout

```text
setVolume      = reps * weightKg
exerciseVolume = sum(setVolume)
workoutVolume  = sum(exerciseVolume)
completionRate = completedEligible / scheduledEligible
```

`scheduledEligible` chỉ gồm schedule có ngày đến hạn trong khoảng báo cáo,
không gồm `CANCELLED` và không gồm ngày hiện tại khi còn session active hoặc
chưa qua cutoff + grace period. `completedEligible` là phần trong mẫu số có
status `COMPLETED`; 0/0 trả `null` kèm counts, không trả 0%. Sau cutoff không
cho cancel để né mẫu số. Metric/PR chỉ dùng log từ session `COMPLETED`.

Seed `rules-v1` phải cố định code, threshold, priority và tie-break theo SRS;
Rule Engine chọn tối đa ba signal khác loại theo `priority DESC, code ASC`.

### Nutrition

```text
entryMetric = foodMetricPerServing * servingMultiplier
dailyMetric = sum(entryMetricSnapshot)
remaining   = target - dailyMetric
```

Snapshot entry gồm tên món, serving và bốn metric calories/protein/carbs/fat.
Không cập nhật lịch sử khi Admin sửa `foods`. Dữ liệu có `is_estimated = true`
phải được API/UI trình bày là tham khảo.

## 14. Security, privacy và logging

- Password, refresh token và OTP chỉ lưu hash; không log plaintext.
- Query private resource luôn filter ownership ở Backend, kể cả khi ID hợp lệ.
- AI consent được kiểm tra trước khi đọc/build personal context.
- `ai_context_snapshots.context_data`, `source_metrics`, audit change summary và
  validation details phải qua whitelist/redaction và có retention hữu hạn.
- Không lưu AI provider credential, API key, access token, full system prompt
  hoặc SQL/endpoint command trong action payload.
- Presigned URL không được lưu như durable credential; chỉ lưu `object_key`.
- Audit denial/mutation nhạy cảm bằng `correlation_id`; không biến audit thành
  kho sao chép raw PII.
- Môi trường đồ án tốt nghiệp chỉ dùng dữ liệu synthetic/demo. Runbook phải reset/purge
  database và object storage trước khi bàn giao hoặc trong vòng 30 ngày sau khi
  kết thúc chấm. Legal retention, self-service deletion và backup expiry phải
  được khóa bằng ADR trước khi dùng dữ liệu thật/production.
